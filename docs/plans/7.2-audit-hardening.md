# Phase 7.2 Cryptographic Audit Hardening Plan

## 1. Objective and Security Scope
Harden the SQLite audit log against tampering, concurrent insertion races, and replacement attacks by implementing a cryptographic SHA-256 hash chain, strict transaction serialization, trigger defenses, offline verification tooling, and external head-hash anchoring.

## 2. Invariants and Database Protections
1. **Transaction Isolation**: All audit chain append operations must execute inside a `BEGIN IMMEDIATE` transaction to eliminate SQLite race conditions and prevent chain branching or head collisions.
2. **Recursive Trigger Enforcement**: `PRAGMA recursive_triggers = ON;` must be set on all database connections to prevent indirect mutation bypasses.
3. **Conflict Guard (BEFORE INSERT)**: Add a `BEFORE INSERT ON audit` trigger that rejects attempts to insert with an invalid `prev_hash` or explicit `id` overrides, blocking `INSERT OR REPLACE` / table-rewrite circumventions.
4. **Append-Only Immutability**: Triggers `trg_audit_no_update` and `trg_audit_no_delete` remain enforced to reject modifications or deletions.

## 3. Cryptographic Chain Specification
Each record $i$ computes:
- $\text{prev\_hash}_i = \text{record\_hash}_{i-1}$ (for genesis record $i=1$: $64 \text{ zeros}$).
- $\text{record\_hash}_i = \text{SHA256}(\text{prev\_hash}_i \parallel ":" \parallel \text{str}(ts) \parallel ":" \parallel kind \parallel ":" \parallel target)$

## 4. External Head-Hash Anchoring
- **Periodic Head Anchor**: A background routine logs the current head hash and timestamp to an append-only file outside the database directory (`logs/audit_head.anchor`).
- **Honest Security Boundary (Threat Model)**:
  - *What It Protects*: Detects retroactive database truncation, table reconstruction, and historical tampering performed after the anchor timestamp.
  - *What It Does Not Protect*: Does not prevent an attacker with root / OS write access from deleting or modifying both the database and the external anchor file simultaneously, nor does it detect un-anchored modifications that occur within the interval between two consecutive anchor writes.

## 5. Verification Command CLI
Implement an offline verification command:
```bash
python -m app.audit verify [--db-path data/assistant.db]
```
The command iterates the complete chain, recomputes hashes sequentially, validates consistency against `logs/audit_head.anchor`, and exits with code `0` on success or code `1` with exact record mismatch coordinates.
